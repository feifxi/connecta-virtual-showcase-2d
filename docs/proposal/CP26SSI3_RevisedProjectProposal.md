## 2. ความเป็นมาและความสำคัญของปัญหา (Background and Problem Statement)

หัวข้อนี้เริ่มจากประสบการณ์ของสมาชิกในทีมที่มักเข้าร่วมงานด้านเทคโนโลยี เช่น Tech Conference และ Tech Meetup แบบออนไลน์ เพราะติดข้อจำกัดด้านเวลาและการเดินทาง แล้วพบว่าสิ่งที่ทำได้มีเพียงการรับชมและพิมพ์ข้อความในแชท ไม่สามารถเดินดูว่าในงานมีบูธอะไรบ้าง พูดคุยกับคนในงาน หรือสร้างเครือข่ายใหม่ได้เหมือนงานในสถานที่จริง จากการสอบหัวข้อโครงงาน กรรมการชี้ว่าเป้าหมาย "งานอีเวนต์ทุกประเภท" กว้างเกินไป ทำให้ต้องแข่งกับเครื่องมือที่องค์กรมีอยู่แล้วอย่าง Microsoft 365 และ Google Workspace ทีมจึงจำกัดขอบเขตลงมาที่ประเภทงานที่เครื่องมือประชุมออนไลน์ทำได้ไม่ดีที่สุด คือ **งานนำเสนอผลงาน (Project Showcase และ Poster Session)** ซึ่งทีมเข้าถึงได้โดยตรงและทดสอบกับผู้ใช้จริงได้

หัวใจของงานนำเสนอผลงานคือ **การคุยสดระหว่างผู้นำเสนอกับผู้ชม** และ **การได้คะแนนและ Feedback** เมื่อผู้ชมมาร่วมงานในสถานที่ไม่ได้ หรือผู้จัดต้องจัดงานออนไลน์ด้วยเครื่องมือที่มีอยู่ สิ่งเหล่านี้หายไป รูปแบบที่ใช้กันทั่วไปคือการเปิดห้องวิดีโอคอลหนึ่งห้องต่อหนึ่งผลงาน ซึ่งงานประชุมวิชาการ ICML และ ICLR ปี 2020 รายงานว่าผู้นำเสนอจำนวนมากนั่งรอคนเดียวตลอดสองชั่วโมง เพราะผู้ชมมองไม่เห็นว่าห้องไหนมีคนคุยอยู่และไม่กล้ากดเข้าห้องของคนที่ไม่รู้จัก [1] ส่วนการแสดงผลงานแบบแกลเลอรีหรือวิดีโอย้อนหลังก็ถามคำถามเจ้าของผลงานไม่ได้ ผู้ชมที่เจอผลงานจำนวนมากไม่รู้ว่าควรดูอะไรก่อน และโอกาสได้พบเจ้าของผลงานจริงต่ำ [2]

ในฝั่งผู้จัดและกรรมการ การให้คะแนนยังทำด้วยกระดาษหรือ Spreadsheet แยกจากกัน ต้องคีย์ข้อมูลซ้ำ รวมคะแนนช้า และ Feedback ถึงนักศึกษาช้า [3][4] ผู้จัดยังไม่มีข้อมูลว่าผลงานใดได้รับความสนใจและผู้ชมแวะนานเท่าใด ซึ่งกรรมการภายนอกมองว่าเป็นข้อมูลที่มีค่าที่สุดที่แพลตฟอร์มจะให้ผู้จัดได้ เมื่อผู้จัดลองใช้แพลตฟอร์มพื้นที่เสมือนอย่าง Gather ก็ต้องสร้างแผนที่และวางบูธเอง ไม่มีเครื่องมือให้คะแนน และเมื่อมีคนรอบโปสเตอร์เกิน 4–5 คนก็คุยกันไม่รู้เรื่องจนต้องย้ายไปใช้ Zoom ควบคู่ [1][5] สุดท้ายเมื่องานจบ ผลงานก็ไม่มีที่ให้คนที่พลาดงานเข้ามาดูต่อ

ทีมสรุปปัญหาเป็นข้อความเดียวว่า **งานนำเสนอผลงานที่จัดออนไลน์หรือมีผู้ชมที่มาร่วมไม่ได้ สูญเสียการพูดคุยสดระหว่างผู้นำเสนอกับผู้ชม ขณะที่ผู้จัดต้องประกอบเครื่องมือหลายตัวเพื่อให้คะแนนและไม่ได้ข้อมูลว่างานได้ผลหรือไม่** ปัญหาที่เป็นพฤติกรรมของผู้ใช้ไม่ใช่การขาดระบบ คือผู้ชมไม่กล้าเข้าห้องของคนแปลกหน้า และผู้ชมเลือกไม่ถูกว่าจะดูผลงานใดเมื่อมีจำนวนมาก

Connecta จึงถูกเสนอเป็นแพลตฟอร์มงานนำเสนอผลงานออนไลน์ ที่ผู้ชมควบคุมตัวละครเดินไปตามบูธในโลกเสมือน 2 มิติ เห็นจากด้านนอกว่าบูธใดมีผู้นำเสนออยู่และมีคนคุยอยู่กี่คน แล้วเดินเข้าไปคุยด้วยเสียงได้ทันทีโดยไม่ต้องกดเข้าห้อง ผู้จัดได้ฮอลล์ที่สร้างจากรายการผลงานโดยอัตโนมัติ กรรมการให้คะแนนตาม Rubric ได้ในบูธระหว่างฟังการนำเสนอ และหลังงานผู้จัดได้รายงานเชิงพื้นที่ว่าผลงานใดมีคนแวะและแวะนานเท่าใด ทั้งนี้ Connecta ไม่ได้มาแทนงานในสถานที่ เพราะงานอย่าง IT BANGMOD D-Day ที่จัดในสถานที่ก็ได้ผลดี (ผู้ร่วมงาน 600 คนขึ้นไป 39 ผลงาน) [6] แต่วางตัวเป็นส่วนขยายแบบ Hybrid สำหรับคนที่มาไม่ได้ เช่น บริษัท ศิษย์เก่า ผู้ปกครอง นักเรียนต่างจังหวัด เป็นเครื่องมือหลักของงานนำเสนอโปสเตอร์ในรายวิชาซึ่งจัดบ่อยและไม่คุ้มจองสถานที่ และเปิดฮอลล์ให้เดินชมต่อหลังงานจบ

โครงงานสอดคล้องกับเป้าหมายการพัฒนาที่ยั่งยืนข้อที่ 4 (Quality Education) เป็นหลัก เพราะนักศึกษาได้ Feedback จากผู้ชมและกรรมการมากขึ้น และนักเรียนต่างจังหวัดเข้ามาดูผลงานและคุยกับรุ่นพี่ได้โดยไม่ต้องเดินทาง สอดคล้องกับข้อที่ 10 (Reduced Inequalities) ในการเปิดให้ผู้ที่เดินทางไม่สะดวกเข้าร่วมได้เท่าเทียม และข้อที่ 13 (Climate Action) ในเชิงคุณภาพจากการลดการเดินทางและโปสเตอร์กระดาษ โดยไม่อ้างตัวเลขการลดคาร์บอน

## 3. วัตถุประสงค์ (Objectives)

1. เพื่อพัฒนาฮอลล์นำเสนอผลงานแบบ 2 มิติ ที่ผู้ใช้ควบคุมตัวละครเดินไปตามบูธ เห็นตำแหน่งผู้อื่นแบบ Real-time และสนทนาด้วยเสียงและข้อความกับผู้ที่อยู่ในระยะใกล้ รองรับผู้ใช้พร้อมกัน 150 คนต่อฮอลล์ และไม่เกิน 300 คน
2. เพื่อพัฒนาระบบบูธผลงานที่ผู้ชมเข้าบูธได้ด้วยการเดินเข้าไป ได้ยินผู้นำเสนอชัดเจนเท่ากันทุกคนในบูธ (เสียงโซนบูธ) ดูโปสเตอร์และหน้าจอที่ผู้นำเสนอแชร์ และค้นหาผลงานแล้วเดินไปยังบูธได้ทันที
3. เพื่อพัฒนาระบบให้คะแนนสำหรับกรรมการ ที่ให้คะแนนตาม Rubric ถ่วงน้ำหนักได้ในบูธ รวมคะแนนอัตโนมัติ และส่ง Feedback ถึงผู้นำเสนอหลังประกาศผล
4. เพื่อพัฒนาระบบจัดการงานแบบ Self-service สำหรับผู้จัด ครอบคลุมการสร้างงาน การนำเข้าผลงานแล้ววางบูธในฮอลล์อัตโนมัติ การเชิญผู้นำเสนอและกรรมการทางอีเมล การจำกัดผู้เข้าร่วมตามโดเมนอีเมล และเครื่องมือดูแลความเรียบร้อย (Mute, Kick, Ban)
5. เพื่อพัฒนาระบบรายงานหลังงาน (Post-event Analytics) ที่บอกได้ว่าบูธใดมีคนแวะ แวะนานเท่าใด และช่วงเวลาใดมีคนมาก พร้อม Feedback และ Popular Vote จากผู้ชม และเปิดฮอลล์ให้เดินชมต่อหลังงาน (Exhibition)
6. เพื่อประยุกต์ใช้ AI ช่วยผู้นำเสนอและผู้จัด ด้วยผู้ช่วยตอบคำถามเกี่ยวกับผลงานจากเอกสารของทีม (Retrieval-Augmented Generation) และการสรุป Feedback
7. เพื่อศึกษาความเป็นไปได้ทางเทคนิคของเสียงตามระยะผ่านสถาปัตยกรรม SFU วัดขีดจำกัดจำนวนผู้ใช้พร้อมกัน Bandwidth และต้นทุนโครงสร้างพื้นฐานต่องาน และประเมินผลกับงานนำเสนอผลงานจริงอย่างน้อย 1 งาน

## 4. กระบวนการได้มาซึ่งหัวข้อโครงงาน

### 4.1 Empathize

**จุดตั้งต้นจากประสบการณ์ตรงของทีม** — สมาชิกในทีมเข้าร่วมงานเทคโนโลยีแบบออนไลน์แล้วพบว่าทำได้เพียงรับชมและพิมพ์แชท ขาดการเดินดูบูธ การคุยกับคนในงาน และการสร้างเครือข่าย ทีมจึงตั้งสมมติฐานว่าพื้นที่เสมือนที่เดินได้จะคืนคุณค่าส่วนนี้ให้ผู้เข้าร่วมงานออนไลน์

**ความเห็นจากการสอบหัวข้อโครงงาน** — กรรมการภายนอกตั้งคำถามหลักว่า Value ที่ผู้จัดยอมจ่ายคืออะไร ต่างจากการดูย้อนหลังอย่างไร และทำไมไม่ใช้ Microsoft 365 หรือ Google Workspace ที่องค์กรมีอยู่แล้ว พร้อมแนะนำให้ตีกรอบกลุ่มเป้าหมายให้ชัด และชี้ว่ารายงานข้อมูลหลังงานคือสิ่งที่มีค่าที่สุดที่ระบบมอบให้ผู้จัดได้ ทีมจึงทบทวนว่างานประเภทใดได้ประโยชน์จากการเดินและคุยในพื้นที่มากที่สุด

**ข้อมูลทุติยภูมิ** — ทีมศึกษางานนำเสนอผลงานที่จัดออนไลน์จริง เช่น NeurIPS 2020 ที่ใช้ Gather จัด Poster Session ผู้เข้าร่วมกว่า 18,000 คน และผู้ร่วม Poster Session ร้อยละ 75 ชอบรูปแบบนี้ [1] ICML และ ICLR ที่ใช้ Zoom หนึ่งห้องต่อหนึ่งโปสเตอร์แล้วผู้นำเสนอนั่งรอคนเดียว [1] Oregon State University ที่ใช้ SpatialChat แล้วผู้ร่วมงานอยู่นานขึ้นและนัดคุยต่อมากขึ้น (ข้อมูลจากผู้ให้บริการ) [7] และงาน ASA 2026 ที่ใช้ข้อมูลเวลาดูโปสเตอร์วางแผนงานปีถัดไป [2]

**ข้อมูลปฐมภูมิ** — ทีมเก็บแบบสอบถามออนไลน์เรื่องประสบการณ์และความต้องการในการเข้าร่วมงาน ได้ผู้ตอบ 27 คน และสัมภาษณ์ผู้เชี่ยวชาญจากภาคอุตสาหกรรมในช่วง Student Consultation ของงาน LINE DEVELOPER CONFERENCE 2026 ผลอยู่ในหัวข้อ 7.4

### 4.2 Define

ทีมแยกปัญหาเป็นสองระดับเพื่อใช้ตัดสินใจทุกครั้งที่มีทางเลือกในการออกแบบ

**ปัญหาหลัก — สิ่งที่เครื่องมือประชุมออนไลน์แก้ไม่ได้:** ผู้ชมที่มาร่วมงานไม่ได้ไม่ได้คุยสดกับผู้นำเสนอ เพราะรูปแบบห้องต่อผลงานทำให้ผู้ชมไม่เห็นว่าห้องไหนมีคนคุยและไม่กล้าเข้า ผู้นำเสนอจึงนั่งรอ และเมื่อมีคนรอบผลงานมากก็คุยกันไม่รู้เรื่อง ประเด็นนี้เป็นเหตุผลเดียวที่โครงงานต้องใช้พื้นที่เสมือน 2 มิติ

**ปัญหารอง — สิ่งที่ทำให้ผู้จัดยังไม่เปลี่ยนมาใช้:** การให้คะแนนและส่ง Feedback กระจายอยู่หลายเครื่องมือ ผู้จัดไม่ได้ข้อมูลว่างานได้ผลหรือไม่ และการเตรียมพื้นที่เสมือนเองใช้เวลามาก ประเด็นนี้ไม่ต้องใช้พื้นที่เสมือน แต่เป็นเงื่อนไขที่ทำให้ระบบถูกนำไปใช้จริง จึงกำหนดให้เครื่องมือจัดงาน ให้คะแนน และ Analytics เป็นองค์ประกอบที่ต้องมีควบคู่กัน

| พื้นที่เสมือนทั่วไป (Gather, SpatialChat) | เดินชมและคุยตามระยะได้ | ผู้จัดสร้างแผนที่เอง ไม่มีเครื่องมืองานนำเสนอ บูธคนเยอะคุยไม่รู้เรื่อง | ไม่เลือก |
| โลก 2 มิติ + เครื่องมืองานนำเสนอในระบบเดียว | แก้ได้ทั้งปัญหาหลักและปัญหารอง ใช้ผ่าน Browser ได้ทันที ต้นทุนเนื้อหาต่ำกว่า 3 มิติ | งานด้าน Real-time และเสียงยากกว่า Web ทั่วไป | เลือก |

### 4.4 Prototype & Test

ทีมประเมินว่าความเสี่ยงหลักอยู่ที่เทคนิค จึงทำ Technical Spike ต่อเนื่องตั้งแต่ก่อนเสนอหัวข้อจนถึงปัจจุบัน (S1–S4) ครอบคลุมโลก 2 มิติบน Browser การซิงโครไนซ์ตำแหน่ง การสื่อสารด้วยเสียงและวิดีโอผ่าน SFU และการเลือกฟังตามระยะ พร้อม Load Test วัดขีดจำกัดของระบบ และทำ UI Mockup ครบทุกหน้าของ Release 1–3 ผลอยู่ในหัวข้อ 7

## 5. จุดเด่นของระบบที่เสนอ

### 5.1 เดินชมและคุยสดโดยไม่ต้องกดเข้าห้อง

**คู่เทียบ:** Zoom, Microsoft Teams, Google Meet, Symposium, Fourwaves

ผู้ชมเดินไปตามบูธ เห็นจากด้านนอกว่าบูธใดมีผู้นำเสนออยู่ (ป้าย ● Live) และมีคนอยู่กี่คน เมื่อยืนใกล้บูธจะเห็นชื่อผลงานก่อน แล้วเดินเข้าพรมบูธเพื่อเข้าร่วมได้ทันที ไม่มี "ประตู" ที่ต้องกล้ากด ส่วนพื้นที่ทางเดินก็คุยกับคนที่อยู่ใกล้ได้เหมือนเดินคุยกันในงานจริง

**การวิเคราะห์ความแตกต่าง:** Microsoft Teams รองรับ Breakout Room ได้ถึง 1,000 คน 200 ห้อง [8] ความจุจึงไม่ใช่ปัญหา ปัญหาคือรูปแบบห้องต่อผลงานแบบเดียวกับที่ ICML/ICLR พบ ผู้ชมมองไม่เห็นว่าข้างในมีอะไรเกิดขึ้น ส่วน Symposium และ Fourwaves ใช้ห้องวิดีโอไม่เกิน 8 คนต่อผลงาน [9][10] Connecta เปลี่ยนการตัดสินใจเข้าห้องเป็นการเดินผ่าน ซึ่งเป็นพฤติกรรมที่ผู้ชมทำอยู่แล้วในงานจริง

### 5.2 เสียงโซนบูธ: บูธที่คนเยอะยังคุยรู้เรื่อง

**คู่เทียบ:** Gather, SpatialChat

ทุกคนบนพรมบูธได้ยินผู้นำเสนอชัดเท่ากันเหมือนอยู่ห้องเดียว ไม่ได้ยินเสียงจากทางเดิน และคนนอกบูธไม่ได้ยินเสียงในบูธ ผู้ชมเห็นหน้าจอที่ผู้นำเสนอแชร์เฉพาะตอนอยู่ในบูธ และผู้นำเสนอปิดไมค์ผู้ชมในบูธตัวเองได้

**การวิเคราะห์ความแตกต่าง:** เสียงตามระยะอย่างเดียวทำให้คนที่ยืนวงนอกได้ยินผู้นำเสนอเบาลง NeurIPS 2020 จึงต้องย้ายไป Zoom เมื่อมีคนรอบโปสเตอร์เกิน 4–5 คน [1] Connecta ออกแบบเสียงตามประเภทพื้นที่ คือทางเดินใช้เสียงตามระยะ และบูธใช้เสียงโซน

### 5.3 ฮอลล์สร้างจากรายการผลงานโดยอัตโนมัติ

**คู่เทียบ:** Gather, SpatialChat

ผู้จัดเลือกฮอลล์จาก Template ใส่รายการผลงานพร้อมหมวด (หรือนำเข้าจากไฟล์ CSV) ระบบวางบูธให้ตามหมวดเป็นโซนสีต่างกัน และผู้นำเสนอแต่งบูธของตนเองหลังรับคำเชิญทางอีเมล

**การวิเคราะห์ความแตกต่าง:** ในแพลตฟอร์มพื้นที่เสมือนทั่วไป ผู้จัดต้องสร้างแผนที่และวางโปสเตอร์ทีละชิ้นเอง [11][5] ซึ่งเป็นภาระที่ทำให้ผู้จัดงานนำเสนอที่จัดบ่อยไม่เลือกใช้

### 5.4 ให้คะแนนในบูธและรวมคะแนนอัตโนมัติ

**คู่เทียบ:** กระดาษและ Spreadsheet, Devpost, Symposium

ผู้จัดตั้ง Rubric พร้อมน้ำหนักและมอบหมายผลงานให้กรรมการ กรรมการเดินไปบูธ ฟังการนำเสนอ ถามสด และให้คะแนนจากแผงบูธได้ทันที แก้ไขได้จนงานจบ ระบบรวมคะแนนถ่วงน้ำหนักให้ และส่ง Feedback ของกรรมการถึงผู้นำเสนอหลังประกาศผล

**การวิเคราะห์ความแตกต่าง:** งานที่ใช้กระดาษต้องคีย์ซ้ำและรวมคะแนนช้า [3] Devpost ถ่วงน้ำหนักคะแนนไม่ได้ [4] ส่วน Symposium มีระบบให้คะแนนครบแต่ไม่มีการเดินชม [9] Connecta รวมการฟังนำเสนอและการให้คะแนนไว้ในที่เดียวกัน

### 5.5 Analytics เชิงพื้นที่หลังงาน

**คู่เทียบ:** แพลตฟอร์มทุกราย

ระบบบันทึกเหตุการณ์ทุกครั้งที่ผู้ชมเข้าและออกจากบูธ ผู้จัดจึงเห็นจำนวนผู้แวะต่อบูธ เวลาที่อยู่ในบูธ Heatmap ของฮอลล์ บูธที่คนเดินผ่านแต่ไม่แวะ ช่วงเวลาที่คนมาก และสัดส่วนผู้ที่กด Interested เทียบกับผู้ที่มาจริง แยกตามประเภทผู้ชม เช่น นักศึกษา บริษัท ศิษย์เก่า ส่วนผู้นำเสนอได้สรุปของบูธตนเอง ทั้งจำนวนผู้แวะ Feedback และคะแนน

**การวิเคราะห์ความแตกต่าง:** ห้องวิดีโอบอกได้เพียงจำนวนผู้เข้าห้อง แต่การรู้ตำแหน่งของผู้ชมในฮอลล์ทำให้ระบบวัดความสนใจได้ละเอียดแบบเดียวกับที่ ASA ใช้วางแผนงานปีถัดไป [2] และเป็นข้อที่กรรมการภายนอกมองว่ามีค่าที่สุด

### 5.6 งานไม่หายไปเมื่อจบ: Exhibition และ AI ผู้ช่วย

**คู่เทียบ:** แกลเลอรีผลงานและวิดีโอย้อนหลัง

หลังจบงานฮอลล์ยังเปิดให้เดินชมต่อในช่วง Exhibition ผู้ที่พลาดงานยังดูโปสเตอร์ ฝาก Feedback และถามผู้ช่วย AI ที่ตอบจากเอกสารของทีมได้ ส่วนการให้คะแนนปิดไปพร้อมงาน

**การวิเคราะห์ความแตกต่าง:** วิดีโอย้อนหลังถามคำถามไม่ได้ Connecta จึงไม่ต้องให้ผู้จัดเลือกระหว่างงานสดกับการเก็บผลงานไว้ให้ดูต่อ

## 6. Challenges ของระบบ

### 6.1 ด้านเทคนิค

**(1) เสียงตามระยะและเสียงโซนบูธ** — ผู้ใช้ต้องได้ยินเฉพาะคนที่อยู่ใกล้ และสลับกลุ่มที่ได้ยินทันทีเมื่อเดิน การเชื่อมต่อแบบ Peer-to-Peer รองรับได้ราว 6 คน และการต่อใหม่ทุกครั้งที่เดินผ่านกันทำให้เสียงขาด

แนวทางรับมือ: ใช้ SFU (LiveKit) ผู้ใช้ส่งเสียงขึ้น Server ชุดเดียว แล้วเลือกรับเฉพาะเสียงของคนในระยะจากตำแหน่งใน Game Server ผล S4 สลับได้ภายใน 0.4 วินาทีและไม่กะพริบที่ขอบระยะ ส่วนเสียงโซนบูธมี Spike S5 ทดสอบก่อนพัฒนาจริง และมีแผนลดระดับเป็นเสียงตามระยะอย่างเดียวหากไม่ผ่าน

**(2) เครือข่ายและ Server ของมหาวิทยาลัย** — เสียง Real-time ส่งด้วย UDP ซึ่งผ่าน Reverse Proxy แบบ HTTP ไม่ได้ VM ที่ได้รับจากคณะมีเพียง IP ภายในและเข้าจากภายนอกผ่าน Reverse Proxy ของคณะเท่านั้น

แนวทางรับมือ: ขอ Public IP และพอร์ตสำหรับ Media จากฝ่าย IT ควบคู่กับเตรียม LiveKit Cloud เป็นแผนสำรองที่สลับได้ด้วยการเปลี่ยน URL และ Key โดยไม่แก้โค้ด และทดสอบจากเครือข่ายจริงหลายแบบ (บ้าน, Wi-Fi มหาวิทยาลัย, 4G) ใน Spike S7

**(3) Bandwidth ของวิดีโอ** — การแชร์จอ 720p ใช้ราว 1.2–1.4 Mbps ต่อผู้ชม และเป็นคอขวดตัวแรกของทั้งระบบ

แนวทางรับมือ: ผู้ชมรับวิดีโอเฉพาะของบูธที่ยืนอยู่ (ไม่เกิน 2 จอ) ไม่ใช่ทุกจอในฮอลล์ ผู้ชมทั่วไปแสดงตัวด้วย Avatar แทนกล้อง และลดความละเอียดลงเป็นระดับกลางได้ซึ่งลด Bandwidth ราว 3 เท่า

**(4) การซิงโครไนซ์ตำแหน่งเมื่อคนเยอะ** — ทุกคนต้องรู้ตำแหน่งของทุกคนในฮอลล์ ข้อมูลที่ Server ส่งออกจึงโตแบบกำลังสองตามจำนวนคน

แนวทางรับมือ: ส่งเฉพาะส่วนที่เปลี่ยน (Delta) ที่ 15 ครั้งต่อวินาที และตั้งเพดาน 300 คนต่อฮอลล์จากผล Load Test หากต้องการเกินนี้ในอนาคตจะส่งเฉพาะคนที่อยู่ในระยะ (Colyseus StateView)

**(5) การควบคุมสิทธิ์หลายบทบาทและการแยกข้อมูลระหว่างงาน** — บทบาทอยู่ระดับงาน ผู้ใช้คนเดียวเป็นกรรมการในงานหนึ่งและผู้ชมในอีกงานได้ และบทบาทเปลี่ยนได้ระหว่างงาน

แนวทางรับมือ: ไม่เชื่อข้อมูลจาก Client ตรวจสิทธิ์ที่ Server ครบ 3 ช่องทาง คือ REST, ข้อความผ่าน WebSocket และตอนออก Token ของ LiveKit ไม่ฝังบทบาทไว้ใน JWT แต่ตรวจจากฐานข้อมูลทุกครั้ง และป้ายบทบาทบนตัวละครออกจาก Server เพื่อกันการปลอมเป็นกรรมการ

**(6) ทีมไม่มีประสบการณ์ในเทคโนโลยีหลัก** — ทีม 3 คนไม่เคยพัฒนาระบบ Real-time เสียง หรือ Phaser มาก่อน และ AI มักเขียนโค้ดของ Phaser 3 ปนเข้ามาใน Phaser 4

แนวทางรับมือ: ทำ Spike ทีละเรื่องและหยุดรายงานผลก่อนเริ่มเรื่องถัดไป ตรวจ API กับเอกสารของเวอร์ชันที่ติดตั้งจริงทุกครั้ง และจัดลำดับ Core ห้ามตัด 5 ข้อไว้ล่วงหน้า (หัวข้อ 8.3)

### 6.2 ด้านธุรกิจและผู้ใช้งาน

**(7) ทำไมต้องออนไลน์ในเมื่องานในสถานที่ก็ได้ผล** — งานอย่าง IT BANGMOD D-Day จัดในสถานที่ได้ดี และงานมหกรรมอาชีพแบบเสมือนมีผู้เข้าร่วมลดลงหลังโควิด [12]

แนวทางรับมือ: วางตำแหน่งเป็นส่วนขยาย Hybrid สำหรับคนที่มาไม่ได้ เครื่องมือหลักของงานโปสเตอร์ในรายวิชา และ Exhibition หลังงาน ไม่ใช่การแทนงานในสถานที่ และยืนยันความต้องการด้วยแบบสอบถามและการสัมภาษณ์ผู้จัด

**(8) ผู้ใช้ที่ไม่คุ้นกับโลก 2 มิติ** — หากไม่เข้าใจวิธีใช้ในไม่กี่นาทีแรก ผู้ใช้อาจออกก่อนได้คุย

แนวทางรับมือ: คลิกเพื่อเดิน เลือกบูธจากรายการแล้วตัวละครเดินไปเองด้วยความเร็วสูง เข้าบูธด้วยการเดินเข้าพรมโดยไม่มีปุ่มให้เรียนรู้ มีคำแนะนำในฮอลล์ครั้งแรก และทดสอบกับผู้ที่ไม่เคยใช้ระบบลักษณะนี้

**(9) ความปลอดภัยของผู้ใช้และ PDPA** — เสียงตามระยะทำให้คนก่อกวนพูดใส่ผู้อื่นได้ทันที และระบบเก็บข้อมูลส่วนบุคคลของผู้เข้าร่วม

แนวทางรับมือ: บังคับ Login ทุกคนไม่มี Guest เพื่อให้ Ban ได้ผล ไมค์ปิดเป็นค่าเริ่มต้น ผู้นำเสนอและผู้จัดปิดไมค์ผู้อื่นได้แต่ไม่มีใครเปิดไมค์ให้ผู้อื่นได้ แชทตามระยะและเสียงไม่ถูกบันทึก แจ้งชัดเจนว่าข้อมูลใดคนอื่นเห็น และการฝากช่องทางติดต่อให้ทีมเป็นแบบทางเดียวที่ผู้ชมถอนได้

**(10) หัวข้อที่ทับกับทีมอื่นในรุ่น** — มีทีมที่ทำระบบจัดการเข้าชมและประเมินโครงงานปี 4

แนวทางรับมือ: จุดต่างของ Connecta คืองานออนไลน์ที่ผู้ชมเดินชมและคุยสดกับผู้นำเสนอได้ และกรรมการให้คะแนนในบูธระหว่างฟังการนำเสนอ

## 7. การศึกษาความเป็นไปได้เบื้องต้น (Feasibility Studies)

การศึกษาในหัวข้อนี้ตอบ Challenges ในหัวข้อ 6 ว่าทำได้จริง ด้านเทคนิคตอบข้อ (1) (3) (4) (5) ด้วย Spike และ Load Test ข้อ (2) อยู่ใน Spike S7 ส่วนด้านธุรกิจตอบข้อ (7) ด้วยกรณีการใช้งานจริง ข้อมูลคู่แข่ง และข้อมูลจากผู้ใช้

### 7.1 ผลการทดลองทางเทคนิค (Technical Spike)

ทุก Spike อยู่ในแอปทดลองเดียวกันและต่อยอดกันตามลำดับ ทดสอบด้วยสคริปต์อัตโนมัติ (Playwright + Chrome) ที่รันซ้ำได้

| Spike | คำถาม | ผล | ข้อสรุป |
|---|---|---|---|
| S1 Phaser 4 + Tiled + Next.js | แสดงโลก 2 มิติจากแผนที่ Tiled ตรวจการชน และทำงานร่วมกับ Next.js ได้หรือไม่ | ผ่าน: 58 fps เดินชนกำแพงและโต๊ะบูธถูกต้อง คลิกเพื่อเดินได้ Mount/Unmount 100 รอบหน่วยความจำคงที่ | ใช้ Phaser 4 + Tiled ได้ ไม่ต้องทำ Map Editor เอง |
| S2 LiveKit | เสียง กล้อง และแชร์จอผ่าน SFU ทำงานได้หรือไม่ | ผ่าน: เข้าห้อง 0.2–1.6 วินาที ภาพจอแรก 0.5 วินาที หยุดแชร์แล้วอีกฝั่งเห็นใน 28 ms | ใช้ LiveKit ได้ ต้องออก Token จาก Server เท่านั้น |
| S3 Movement Sync + Load Test | ซิงโครไนซ์ตำแหน่ง 150 คนต่อฮอลล์ได้ลื่นหรือไม่ และกันการโกงตำแหน่งได้หรือไม่ | ผ่าน: 150 คนใช้ CPU Server ไม่เกิน 7% ข้อมูล 11.6 KB/s ต่อคน หน้าเว็บ 60 fps ทดสอบถึง 1,000 คน Server ยังไม่ตัน | ใช้ Colyseus 15 ครั้งต่อวินาที เพดาน 300 คนต่อฮอลล์ |
| S4 Proximity Media | เข้าใกล้ได้ยิน เข้าบูธเห็นจอ ออกแล้วหาย เร็วแค่ไหน และ Browser รับได้กี่ Track | ผ่าน 12/12 ทั้ง 3 รอบ: สลับภายใน 0.4 วินาที ไม่กะพริบที่ขอบระยะ รับเสียง 40 Track เพิ่ม CPU ราว 15% | ภาระหลักคือวิดีโอ จึงให้เห็นเฉพาะจอของบูธที่ยืนอยู่ |

Spike ที่เหลือ: S5 เสียงโซนบูธ, S6 โปสเตอร์และโมเดล 3 มิติที่ซูมตามกัน และ S7 การเชื่อมต่อผ่าน NAT และ TURN บน Server จริง

### 7.2 ขีดความสามารถของระบบ (Capacity)

ทีมวัดขีดความสามารถเป็น **จำนวนผู้ใช้พร้อมกัน** ไม่ใช่จำนวนงาน เพราะงานแต่ละงานมีขนาดต่างกัน และกำหนดเกณฑ์ "รองรับได้" ไว้ล่วงหน้า คือทุกคนได้รับเสียงและภาพครบ Packet Loss ต่ำกว่าร้อยละ 1 Event Loop p99 ของ Game Server ต่ำกว่า 50 ms และ RTT p99 ต่ำกว่า 100 ms แล้วเพิ่มจำนวนผู้ใช้จำลองทีละขั้นจนหลุดเกณฑ์

- **ตำแหน่ง (Colyseus):** ใช้ Bot เดินสุ่มส่งตำแหน่ง 15 ครั้งต่อวินาทีและแวะบูธเป็นระยะ เพิ่มจาก 100 ถึง 1,000 คนในฮอลล์เดียว และ 1 ถึง 16 งานพร้อมกัน ผล: 1 Process รับ 8 งาน × 150 คนได้สบาย
- **เสียงและภาพ (LiveKit):** ใช้ lk perf load-test จำลองสามสถานการณ์ที่ 150 คน คือทุกคนดูจอในบูธ (ส่งออกรวมราว 255 Mbps), เวทีเดียว (ราว 235 Mbps) และคุยเป็นกลุ่ม 8 คน (ราว 56 Mbps)
- **คอขวดตัวแรก:** Bandwidth ขาออกของ Server ส่วนใหญ่มาจากวิดีโอ ตามด้วย CPU ของ LiveKit ขีดความสามารถของ Platform จึงประมาณได้จาก Bandwidth ขาออกหารด้วย Bandwidth ต่อคน เช่น Uplink ที่ใช้ได้ราว 800 Mbps รองรับผู้ชมที่ดูจอ 720p ได้ราว 500 คน (ประมาณ 3 งาน × 150 คน)

ข้อจำกัดของผลชุดนี้คือวัดบนเครื่องเดียวที่ Bot และ Server แย่ง CPU กันและไม่มี Delay ของเครือข่ายจริง ทีมจะวัดซ้ำบน VM จริงโดยยิงจากอีกเครื่อง ทดสอบ 150 คนเข้าพร้อมกันในนาทีแรก และทดสอบต่อเนื่อง 3–4 ชั่วโมงเพื่อหา Memory Leak ก่อน Release 1

### 7.3 ความเป็นไปได้ด้านธุรกิจ

**มีการใช้งานจริงและผู้ใช้ตอบรับ** — NeurIPS 2020 จัด Poster Session ราว 2,000 ชิ้นในพื้นที่ 2 มิติ ผู้ร่วมร้อยละ 75 ชอบ และร้อยละ 8 ไม่ชอบ [1] มหาวิทยาลัยในต่างประเทศ เช่น Syracuse University และ University of Michigan ใช้พื้นที่ 2 มิติจัดงานแสดงผลงานนักศึกษา [13] และ Oregon State University รายงานว่าผู้ร่วม Poster Session ใน SpatialChat อยู่เฉลี่ย 35–45 นาทีจากเดิม 15–20 นาที (ข้อมูลจากผู้ให้บริการ) [7]

**มหาวิทยาลัยจ่ายเงินให้เครื่องมืองานนำเสนอจริง** — Symposium by ForagerOne คิดค่าบริการมหาวิทยาลัย 2,499–3,999 ดอลลาร์สหรัฐต่อปี [9] แสดงว่ามีผู้จ่ายในกลุ่มนี้ แต่เครื่องมือกลุ่มนี้ยังใช้ห้องวิดีโอในช่วง Live

**ช่องว่างในตลาด** — แพลตฟอร์มแบ่งเป็นสองฝั่งที่แยกกัน คือฝั่งประสบการณ์เดินงาน (Gather, SpatialChat) และฝั่งเครื่องมือจัดงานนำเสนอ (Symposium, Fourwaves) Connecta รวมสองฝั่งไว้ในที่เดียวเฉพาะงานนำเสนอผลงาน

| แพลตฟอร์ม | ประเภท | มีอะไร | ยังขาดเมื่อเทียบกับงานนำเสนอ |

- **เห็นด้วยกับการโฟกัสงานนำเสนอผลงาน** เพราะนอกจากเครื่องมือปัจจุบันยังทำส่วนนี้ได้ไม่ดี คู่แข่งในกลุ่มนี้ยังน้อยกว่างานอีเวนต์ทั่วไป
- **ไม่ต้องกลัวการมีคู่แข่ง** เพราะไม่ว่าทำอะไรก็มีคู่แข่ง สิ่งสำคัญคือหาจุดต่างให้ได้
- **ใช้ความเล็กเป็นข้อได้เปรียบ** ผู้ให้บริการที่อยู่มานานมีระบบใหญ่และทีมใหญ่ขึ้น การลองเทคโนโลยีใหม่จึงยากขึ้น ทีมขนาดเล็กปรับตัวและลองของใหม่ได้เร็วกว่าโดยไม่กระทบผู้ใช้จำนวนมาก เช่น นำโมเดล 3 มิติมาใช้ให้การนำเสนอน่าสนใจขึ้น

#### ข้อสรุปจากข้อมูล

ข้อมูลจากผู้ใช้ยืนยันว่า (1) ผู้ชมยังให้คุณค่ากับงานในสถานที่ เพราะได้คุยกับเจ้าของผลงานและเห็นของจริง Connecta จึงต้องคืนสองสิ่งนี้ให้ผู้ที่มาไม่ได้ ไม่ใช่แทนงานจริง (2) อุปสรรคหลักของการมาร่วมงานคือระยะทางและเวลา (3) งานแสดงผลงานนักศึกษาเป็นประเภทงานที่ผู้ตอบเห็นว่าเหมาะที่สุด และผู้เชี่ยวชาญเห็นด้วยกับการโฟกัสนี้ และ (4) ความต้องการโมเดล 3 มิติสูงทั้งจากแบบสอบถามและคำแนะนำของผู้เชี่ยวชาญ ทีมจึงคง Spike S6 (โปสเตอร์และโมเดล 3 มิติที่ซูมตามกัน) ไว้ในแผน สิ่งที่ยังต้องยืนยันคือมุมมองของผู้จัดงานว่ายอมจ่ายเพื่ออะไร

## 8. ระบบที่นำเสนอ (Proposed System)

### 8.1 กลุ่มเป้าหมาย

ทีมแบ่งกลุ่มเป้าหมายจากประเภทงานนำเสนอผลงานและบทบาทในการตัดสินใจจ่าย

| กลุ่ม | ตัวอย่าง | บทบาท | สถานะ |
|---|---|---|---|
| A. คณะหรือภาควิชาที่จัดงานโปรเจคจบ | IT BANGMOD D-Day | ผู้จ่าย (Pro) | กลุ่มหลัก |
| B. อาจารย์รายวิชาที่ให้นำเสนอโปสเตอร์ | วิชาที่มี Poster Session ท้ายภาค | ใช้ Free แล้วนำไปสู่การที่คณะสมัคร Pro | กลุ่มหลัก (ช่องทางเข้า) |
| C. Hackathon และ Demo Day | ช่วงนำเสนอและตัดสินผลงาน | ซื้อ Event Add-on รายงาน | กลุ่มรอง |
| D. Poster Session ของงานประชุมวิชาการ | งานประชุมแบบ Hybrid | Pro + Event Add-on | ขยายภายหลัง |

**ผู้ใช้ภายในงาน:** ผู้นำเสนอ (นักศึกษา) ผู้ชม (นักศึกษา นักเรียนมัธยมปลาย บริษัท ศิษย์เก่า ผู้ปกครอง) กรรมการ (อาจารย์และผู้เชี่ยวชาญจากภาคอุตสาหกรรม) และผู้จัดงาน

**กลุ่มเป้าหมายมีผลต่อการออกแบบ**
- ผู้ชมส่วนใหญ่ไม่เคยใช้โลก 2 มิติ และเข้ามาเพียงครั้งเดียว → คลิกเพื่อเดิน เลือกบูธจากรายการแล้วเดินไปเอง เข้าบูธด้วยการเดินเข้าพรมโดยไม่มีปุ่มให้เรียนรู้ และ Onboarding ไม่เกิน 30 วินาที
- กรรมการจากภาคอุตสาหกรรมมีเวลาจำกัด → ให้คะแนนจากแผงบูธได้ทันทีระหว่างฟัง ไม่ต้องสลับไปหน้าอื่น
- ผู้นำเสนอเป็นนักศึกษาที่ไม่ได้ออกแบบพื้นที่เอง → ฮอลล์และบูธสร้างอัตโนมัติจาก Template แต่งบูธด้วยฟอร์ม
- ผู้จัดเป็นคณะหรืออาจารย์ที่ใช้บัญชีมหาวิทยาลัย → Login ด้วย Microsoft (บัญชีองค์กร) และจำกัดผู้เข้าร่วมตามโดเมนอีเมลได้
- ผู้ชมภายนอก (ผู้ปกครอง นักเรียน) อาจใช้มือถือ → หน้างานและฮอลล์ใช้บนมือถือได้ แม้ออกแบบให้คอมพิวเตอร์เป็นหลัก

**ไม่ใช่กลุ่มเป้าหมาย:** งานแสดงสินค้าและ Marketplace งาน Webinar หรือการบรรยายทางเดียวที่เครื่องมือประชุมออนไลน์ทำได้ดีอยู่แล้ว และงานที่ต้องสัมผัสของจริง

### 8.2 ภาพรวมระบบ

Connecta เป็น Web Application ที่ใช้ผ่าน Browser ไม่ต้องติดตั้งโปรแกรม รวมฮอลล์ 2 มิติเข้ากับเครื่องมือจัดงานนำเสนอไว้ในระบบเดียว ประเภทแอปพลิเคชันคือ Multi-tenant SaaS แบบ Self-service ที่ผู้จัดสร้างและรันงานเอง หน้างาน (ข้อมูลงานและรายการผลงาน) เปิดดูได้โดยไม่ต้อง Login ส่วนการเข้าฮอลล์ การให้ Feedback และการโหวตต้อง Login ทุกครั้ง

**แนวคิดหลัก:** รูปแบบการสื่อสารเปลี่ยนตามพื้นที่ที่ผู้ใช้ยืนอยู่ เหมือนงานในสถานที่จริงที่การยืนคุยในทางเดินกับการเข้าไปฟังที่บูธมีลักษณะต่างกัน

- **ทางเดิน** — ได้ยินคนที่อยู่ในระยะประมาณ 5 ช่อง เสียงเบาลงตามระยะ และแชทกับคนใกล้ ๆ ได้ (ไม่เก็บประวัติ)
- **บูธ** — เข้าด้วยการเดินเข้าพรมบูธ ทุกคนในบูธได้ยินกันชัดเท่ากัน ไม่ได้ยินเสียงนอกบูธ เห็นโปสเตอร์และจอที่ผู้นำเสนอแชร์ ออกด้วยการก้าวออก
- **ทั้งงาน** — แชท Everyone ที่ทุกคนเห็น และประกาศจากผู้จัดที่ขึ้นแถบบนจอของทุกคน

**หลักการสำคัญ:** สิทธิ์พิเศษมีผลเฉพาะพื้นที่ของตน ผู้นำเสนอแชร์จอและปิดไมค์ผู้อื่นได้เฉพาะในบูธของตัวเอง เมื่อออกจากบูธก็ใช้งานเหมือนผู้ชมทั่วไป

**วงจรของงาน:** Draft (ผู้จัดตั้งค่า) → Published (หน้างานเปิด กด Interested ได้) → Live (ฮอลล์เปิด ให้คะแนนได้) → Exhibition (หลังงาน เดินชมต่อได้ การให้คะแนนปิด) → Archived

### 8.3 ฟีเจอร์หรือฟังก์ชันการทำงานที่เป็นความต้องการของระบบ

บทบาทอยู่ระดับงาน ผู้ใช้หนึ่งคนมีได้หลายบทบาทในงานเดียว สิทธิ์ที่ได้คือผลรวมของทุกบทบาท ไม่ใช่ลำดับชั้น บทบาทที่มีสิทธิ์พิเศษได้จากคำเชิญทางอีเมลเท่านั้น และทุกคนต้อง Login ด้วย Microsoft, Google หรือ Magic Link

| บทบาท | ขอบเขต | หน้าที่หลัก |
|---|---|---|
| Visitor | ทั้งงาน | ค่าเริ่มต้นของทุกคนที่เข้างาน |
| Presenter | บูธของตนเอง | แต่งบูธ นำเสนอ แชร์จอ ปิดไมค์คนในบูธ ดูสถิติและ Feedback ของบูธตนเอง |
| Judge | ผลงานที่ได้รับมอบหมาย | ให้คะแนนตาม Rubric เห็นเฉพาะคะแนนของตนเอง |
| Admin | ทั้งงาน (มีได้หลายคน อย่างน้อย 1 คน) | สร้างและจัดการงานทั้งหมด ดูแลความเรียบร้อย ดู Analytics ประกาศผล |
| Platform Admin | ทั้งระบบ | ทีมพัฒนา ดูแลภาพรวมและสถานะของระบบ |

#### ผู้ชม (Visitor)

- ดูหน้างานและรายการผลงานก่อนเข้า ค้นหาและกรองตามหมวด และกด Interested เพื่อรับการแจ้งเตือน
- Login ตั้งโปรไฟล์ครั้งแรก (ชื่อ ตัวละคร ประเภทผู้ใช้ จังหวัด) และกรอกฟอร์มเข้างาน
- เดินในฮอลล์ด้วยการคลิกหรือคีย์บอร์ด เห็นผู้อื่นแบบ Real-time และเลือกบูธจากรายการแล้วตัวละครเดินไปเอง
- คุยด้วยเสียงและข้อความกับคนใกล้ ๆ เข้าบูธเพื่อฟังผู้นำเสนอ ดูโปสเตอร์และจอที่แชร์ และส่ง Reaction
- ฝาก Feedback (เลือกไม่ระบุชื่อได้) โหวต Popular Vote และฝากช่องทางติดต่อให้ทีมผู้นำเสนอ
- ถามผู้ช่วย AI เกี่ยวกับผลงาน และเดินชมต่อในช่วง Exhibition

#### ผู้นำเสนอ (Presenter)

- รับคำเชิญทางอีเมล แต่งบูธ (ชื่อ สรุป Tag ภาพปก ลิงก์ วิดีโอ โปสเตอร์ PDF) และเชิญสมาชิกในทีม
- แก้ข้อมูลบูธได้ทั้งก่อนและระหว่างงาน ทั้งจากหน้าจัดการและจากแผงบูธในฮอลล์
- นำเสนอด้วยเสียง แชร์จอเดโมผลงาน และปิดไมค์ผู้ชมที่รบกวนในบูธของตนเอง
- ดูสรุปบูธหลังงาน ได้แก่ จำนวนผู้แวะ Feedback คะแนนและความเห็นของกรรมการหลังประกาศผล และรายชื่อผู้ที่ฝากช่องทางติดต่อ

#### กรรมการ (Judge)

- เห็น Rubric และรายการผลงานที่ได้รับมอบหมายล่วงหน้า พร้อมสถานะว่าส่งคะแนนแล้วกี่ผลงาน
- เดินไปบูธ ฟังการนำเสนอ ถามสด และให้คะแนนจากแผงบูธได้ทันที หรือให้จากหน้ารายการ (ใช้ API เดียวกัน)
- แก้คะแนนได้จนงานจบ และเขียนความเห็นถึงทีมซึ่งส่งถึงทีมหลังประกาศผล

#### ผู้จัด (Admin)

- สร้างงาน กำหนดเวลาเริ่มและจบ (งานจบเองตามเวลา) จำกัดผู้เข้าร่วมตามโดเมนอีเมล เลือกฮอลล์ Template และจำนวนคนพร้อมกัน
- เพิ่มผลงานหรือนำเข้าจาก CSV/XLSX ระบบวางบูธในฮอลล์ตามหมวดอัตโนมัติ และเชิญผู้นำเสนอและกรรมการทางอีเมล
- ตั้ง Rubric พร้อมน้ำหนัก (ล็อกเมื่อมีคะแนนแรก) มอบหมายผลงานให้กรรมการ และเปิดหรือปิดโมดูล เช่น Judging, Popular Vote, Feedback, AI
- ดูแลความเรียบร้อยจากในฮอลล์: Mute, Kick, Ban รับ Report สวิตช์ฉุกเฉิน และประกาศถึงทุกคน
- ดู Analytics หลังงาน ผลคะแนนรวมถ่วงน้ำหนัก แล้วประกาศผลรางวัลจากกรรมการและ Audience Award

#### ฟีเจอร์ด้าน AI (แผน Pro)

- **ผู้ช่วยตอบเรื่องผลงาน** — ตอบคำถามจากเอกสารที่ทีมอัปโหลดด้วย Retrieval-Augmented Generation ใช้ได้ทั้งตอนผู้นำเสนอไม่อยู่และในช่วง Exhibition
- **สรุป Feedback** — สรุปความเห็นจากผู้ชมให้ผู้นำเสนอ
- **นำเข้าผลงานด้วย AI** — ช่วยจับคู่คอลัมน์จากไฟล์รายการผลงาน

#### ลำดับ Core และขอบเขตที่ระบบรองรับ

หากเวลาไม่พอ ทีมจะตัดจากลำดับท้ายขึ้นมา โดย 5 ข้อแรกห้ามตัด

1. โลก 2 มิติ: เดินในฮอลล์ บูธ เสียงและแชทตามระยะ และ Mute, Kick, Ban
2. บูธ: หน้าบูธ โปสเตอร์ เสียงโซนบูธ และแชร์จอ
3. ค้นหาและกรองผลงานแล้วไปบูธทันที
4. Judging: Rubric ให้คะแนนในบูธ และรวมคะแนน
5. Analytics หลังงานและ Feedback ถึงผู้นำเสนอ

- ผู้ใช้พร้อมกัน 150 คนต่อฮอลล์ เพดาน 300 คน (แผน Free ไม่เกิน 50 คน)
- 1 งาน = 1 ฮอลล์ เมื่อฮอลล์เต็ม ผู้ชมรอแล้วลองใหม่ได้ ไม่มีการจองที่
- ใช้ผ่าน Browser บนคอมพิวเตอร์เป็นหลัก และใช้บนมือถือได้ หน้าจอเป็นภาษาอังกฤษ

### 8.4 สถาปัตยกรรมระบบ

ระบบเป็น **เว็บแอปพลิเคชัน** ที่ใช้ผ่าน Browser ที่รองรับ WebRTC (Chrome, Edge, Safari) บนคอมพิวเตอร์และมือถือ ไม่มีแอปให้ติดตั้ง ระบบแบ่งเป็น Service ที่ทำงานใน Container แยกกันด้วย Docker Compose บน VM ของคณะ มี nginx เป็นทางเข้าเดียวของ HTTP และ WebSocket ส่วนเสียงและวิดีโอที่ส่งด้วย UDP ต่อตรงจาก Browser ไปยัง LiveKit เพราะผ่าน Reverse Proxy แบบ HTTP ไม่ได้

![ภาพที่ 1 สถาปัตยกรรมระบบ](../images/r1-architecture.png)

*ภาพที่ 1 สถาปัตยกรรมระบบ (Release 1)*

| Container | Port / Protocol | หน้าที่ |
|---|---|---|
| nginx | 80 · HTTP, WebSocket | รับทุก Request แล้วส่งต่อตาม Path ไปยังหน้าเว็บ API และ Game Server |
| web (Next.js) | 3001 · HTTP | หน้าเว็บทั้งหมด โลก 2 มิติ (Phaser 4) และระบบ Login (Better Auth) |
| api (NestJS) | 3000 · HTTP REST/JSON | ข้อมูลถาวร สิทธิ์ คำเชิญ การอัปโหลดไฟล์ และการออกบัตรเข้าฮอลล์ |
| realtime (Colyseus) | 2567 · WebSocket | 1 ห้องต่อ 1 ฮอลล์ ตำแหน่งของทุกคน สถานะบูธ และแชทตามระยะ |
| livekit | 7880 + UDP 50000–60000 · WebRTC | SFU ส่งต่อเสียงและวิดีโอ พร้อม TURN สำหรับเครือข่ายที่ถูกปิดกั้น |
| postgres | 5432 · SQL | ฐานข้อมูลหลัก และ pgvector สำหรับ AI |
| minio | 9000 · S3 API | เก็บไฟล์ (ภาพปก โปสเตอร์) ส่งให้ผู้ใช้ด้วยลิงก์ที่หมดอายุได้ |

**Environment:** dev บนเครื่องของสมาชิก และ production บน VM ของคณะ (4 vCPU, 8 GB) ที่เข้าจากภายนอกผ่าน Reverse Proxy ของคณะ **External Entity:** Microsoft Identity Platform และ Google (OAuth 2.0/OIDC), SMTP สำหรับ Magic Link และคำเชิญ, LLM API และ LiveKit Cloud เป็นแผนสำรองของเสียง

**หลักการด้านความปลอดภัย**

1. Token ของ LiveKit ออกจาก Server เท่านั้น และกำหนดว่าใครส่งอะไรได้ เช่น ผู้ชมส่งได้แค่ไมค์ ผู้นำเสนอแชร์จอได้
2. ตรวจสิทธิ์ที่ Server ครบทุกช่องทาง (REST, WebSocket, การออก Token) ไม่พึ่งการซ่อนเมนู
3. ทุกตารางที่เป็นข้อมูลของงานมีรหัสงานกำกับ และทุกคำสั่งค้นหากรองด้วยรหัสงานเสมอ เพื่อกันการเข้าถึงข้อมูลข้ามงาน
4. Game Server ตรวจการเดินทุกครั้ง (โควตาระยะทางและการชนกำแพง) เพื่อกันการโกงตำแหน่ง

### 8.6 ทฤษฎีและระบบที่เกี่ยวข้อง

**Spatial Presence และ Proximity-based Communication** — การสื่อสารเกิดระหว่างผู้ใช้ที่อยู่ใกล้กันในพื้นที่จำลอง แทนการที่ทุกคนได้ยินทุกคน ทำให้เกิดหลายวงสนทนาพร้อมกันใกล้เคียงพฤติกรรมในสถานที่จริง

**Selective Forwarding Unit (SFU)** — ผู้ใช้ส่งสื่อขึ้น Server ชุดเดียว แล้ว Server ส่งต่อให้ผู้รับที่เกี่ยวข้อง ต่างจาก Mesh ที่ผู้ใช้ต้องส่งให้ทุกคนโดยตรง และต่างจาก MCU ที่ Server ต้องรวมสัญญาณซึ่งใช้ทรัพยากรสูง ระบบใช้ SFU ร่วมกับการเลือกรับ (Selective Subscription) ตามตำแหน่ง

**Authoritative Server และ State Synchronization** — Game Server เป็นผู้ตัดสินตำแหน่งจริงและส่งเฉพาะส่วนที่เปลี่ยนแปลงไปยังทุกคน ฝั่งหน้าเว็บใช้ Client Prediction ให้ตัวเราขยับทันที และ Interpolation ให้คนอื่นเคลื่อนที่ลื่น

**Retrieval-Augmented Generation (RAG)** — ค้นส่วนของเอกสารที่เกี่ยวข้องด้วย Vector Search แล้วให้ LLM ตอบจากเนื้อหานั้น ลดการตอบเกินข้อมูลของทีม

### 8.7 โมเดลธุรกิจและขอบเขตเพิ่มเติม

โมเดลธุรกิจเป็น **Freemium + Subscription แบบ Self-service** ผู้จัดสร้างและรันงานเอง ผู้จ่ายคือคณะหรือผู้จัดงาน ผู้เข้าร่วมทุกคนใช้ฟรี และจำกัดที่ขนาดงานไม่จำกัดฟีเจอร์ เพื่อให้ผู้จัดเห็นคุณค่าของ Judging และ Analytics ตั้งแต่งานแรก ส่วนที่คิดเงินคือสิ่งที่เป็นต้นทุนจริง ได้แก่ จำนวนคนพร้อมกัน (Bandwidth ของ Media) และ AI

|   | Free | Pro (รายปี) |
|---|---|---|
| เหมาะกับ | งานในรายวิชา งานขนาดเล็ก | คณะหรือภาควิชาที่จัดงานหลายงานต่อปี |
| คนพร้อมกัน | ไม่เกิน 50 คน | ไม่เกิน 300 คนต่องาน |
| ฟีเจอร์ | ทุกฟีเจอร์ยกเว้น AI กรรมการไม่เกิน 5 คน Exhibition 7 วัน | ทุกฟีเจอร์และ AI กรรมการไม่จำกัด Exhibition 30 วัน |

Event Add-on ให้ผู้ใช้ Free อัปเกรดเฉพาะงานเดียว หรือให้ผู้ใช้ Pro เพิ่มจำนวนคนพร้อมกันสำหรับงานใหญ่ ราคาเป็นเงินบาทจะกำหนดหลังวัดต้นทุนต่องานและคุยกับผู้จัดจริง ในโครงงานนี้ระบบบังคับข้อจำกัดของแผนที่ Server แต่ไม่มีการรับชำระเงินจริง

**สิ่งที่ไม่อยู่ในขอบเขต:** การรับชำระเงินจริง ระบบตั๋ว คิวพบปะตัวต่อตัว นามบัตรเสมือน ตาราง Session และเวทีบรรยาย Map Editor ในเว็บ (ใช้ Template ฮอลล์แทน) และการเก็บประวัติแชทตามระยะ เสียง หรือวิดีโอ
